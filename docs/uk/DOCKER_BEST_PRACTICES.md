## 📌 Правило 01: Використовуйте офіційні образи

- **Чому це важливо:** Офіційні образи на Docker Hub підтримуються профільними командами розробників, регулярно оновлюються, містять патчі безпеки та не містять шкідливого або застарілого коду.

```dockerfile
# ❌ Погано: Невідомий сторонній користувач (ризик вразливостей або бекдорів)
FROM randomuser123/python-flask:latest

# ✅ Добре: Офіційний верифікований образ
FROM python:3.11-slim
```

## 📌 Правило 02: Ніколи не використовуйте tag `:latest` у продакшні

- **Чому це важливо:** Тег `:latest` не є фіксованою версією. Він може оновитися в будь-який момент. Через це ваш білд, який працював учора, сьогодні може зламатися через несумісні зміни у новій версії бібліотеки чи інтерпретатора.

```dockerfile
# ❌ Погано: Непередбачувано, версія може раптово змінитись
FROM node:latest
FROM postgres:latest

# ✅ Добре: Точна, детермінована версія (Pinned version)
FROM node:20.11.0-alpine
FROM postgres:15.6-alpine
```

## 📌 Правило 03: Використовуйте найменші базові образи

- **Чому це важливо:** Менший образ = швидша передача через мережу (`docker pull`/`docker push`), швидший запуск контейнерів, менше споживання диску та значно менша поверхня атаки (менше встановлених утиліт = менше потенційних вразливостей CVE).

| Образ | Приблизний розмір | Призначення |
| :--- | :--- | :--- |
| `python:3.11` (Full) | ~1000 MB | Містить повний набір компіляторів та системних утиліт |
| `python:3.11-slim` | ~120 MB | Містить тільки мінімальний Debian + Python runtime |
| `python:3.11-alpine` | ~50 MB | Ультралегкий дистрибутив Alpine на базі musl libc |

```dockerfile
# ❌ Погано: Зайві 900+ MB непотрібних пакетів
FROM python:3.11

# ✅ Добре: Легкий та швидкий образ
FROM python:3.11-slim
```

## 📌 Правило 04: Не встановлюйте зайвих пакетів

- **Чому це важливо:** Не встановлюйте текстові редактори (`vim`, `nano`), засоби налагодження чи зайві бібліотеки у фінальний образ. Використовуйте прапорець `--no-install-recommends` для `apt-get` та очищуйте кеш пакетів.

```dockerfile
# ❌ Погано: Встановлює сотні непотрібних рекомендованих пакетів і зберігає кеш на диску
RUN apt-get update && apt-get install -y curl vim git wget

# ✅ Добре: Лише потрібні пакети, без зайвого + очищення кешу
RUN apt-get update && apt-get install -y --no-install-recommends \
    curl \
    ca-certificates \
    && rm -rf /var/lib/apt/lists/*
```

## 📌 Правило 05: Використовуйте багатоетапні збірки

- **Чому це важливо:** Дозволяє відокремити важке середовище збірки (компілятори C/C++, SDK, dev-залежності) від фінального образу, де залишаються тільки скомпільовані бінарники або готові бібліотеки.

```dockerfile
# --- Stage 1: Збірка ---
FROM python:3.11-slim AS builder
WORKDIR /app
RUN apt-get update && apt-get install -y --no-install-recommends gcc build-essential
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

# --- Stage 2: Чистий продакшн-образ ---
FROM python:3.11-slim
WORKDIR /app
# Копіюємо лише результат з етапу builder
COPY --from=builder /root/.local /root/.local
COPY . /app
ENV PATH=/root/.local/bin:$PATH
EXPOSE 8080
CMD ["python", "app.py"]
```

## 📌 Правило 06: Один контейнер = один застосунок

- **Чому це важливо:** Контейнер повинен вирішувати одне завдання (Single Responsibility Principle). Не запускайте вебсервер, базу даних і Redis в одному контейнері. Це полегшує масштабування, перезапуск, збір логів та обробку сигналів зупинки (PID 1).

```
❌ Погано:
┌──────────────────────────────────────┐
│  Container: Web App + Postgres + SSH │
└──────────────────────────────────────┘

✅ Добре (Docker Compose / Network):
┌────────────────┐     ┌────────────────┐     ┌────────────────┐
│  Container 1   │ <-> │  Container 2   │ <-> │  Container 3   │
│   (Web App)    │     │  (PostgreSQL)  │     │    (Redis)     │
└────────────────┘     └────────────────┘     └────────────────┘
```

## 📌 Правило 07: Кешування шарів (від стабільних до динамічних)

- **Чому це важливо:** Docker кешує кожен шар згори донизу. Якщо шар змінюється, **всі наступні шари** перезбираються без кешу. Тому файли, які змінюються рідко (залежності), копіюють спочатку, а код, який змінюється постійно — в кінці.

```dockerfile
# ❌ Погано: Будь-яка зміна в app.py змушує наново скачувати всі pip пакети!
COPY . /app
RUN pip install -r requirements.txt

# ✅ Добре: Залежності кешуються і не встановлюються повторно при зміні коду
COPY requirements.txt /app/
RUN pip install --no-cache-dir -r requirements.txt
COPY . /app/
```

## 📌 Правило 08: Розбивайте довгі RUN команди на кілька рядків

- **Чому це важливо:** Кожна інструкція `RUN` створює новий шар. Якщо розбити команди на кілька окремих `RUN`, тимчасові файли залишаться в проміжних шарах назавжди. Об'єднуйте їх через `&& \` для створення одного компактного шару та кращої читабельності.

```dockerfile
# ❌ Погано: Створює 4 окремих шари, тимчасовий кеш займає місце
RUN apt-get update
RUN apt-get install -y curl
RUN apt-get install -y git
RUN rm -rf /var/lib/apt/lists/*

# ✅ Добре: Один шар, легко читати, кеш очищено в тому ж шарі
RUN apt-get update && apt-get install -y --no-install-recommends \
    curl \
    git \
    ca-certificates \
    && rm -rf /var/lib/apt/lists/*
```

## 📌 Правило 09: Віддавайте перевагу COPY над ADD

- **Чому це важливо:** `COPY` прозора, безпечна та просто копіює локальні файли. `ADD` має магічну приховану логіку (може автоматично розпаковувати архіви або завантажувати файли з URL), що часто призводить до неочікуваних багів. Використовуйте `ADD` виключно коли треба розпакувати локальний `.tar` архів.

```dockerfile
# ❌ Погано: Неочевидна поведінка для простих файлів
ADD requirements.txt /app/
ADD app.py /app/

# ✅ Добре: Явно, просто і передбачувано
COPY requirements.txt /app/
COPY app.py /app/

# 💡 Виняток для ADD: Автоматичне розпакування архіву
ADD release-v1.0.tar.gz /app/
```

## 📌 Правило 10: ЗАВЖДИ використовуйте WORKDIR

- **Чому це важливо:** Ніколи не покладайтеся на початкову папку базового образу. Також ніколи не пишіть `RUN cd /app`, оскільки команда `cd` **не зберігає свій стан між шарами Dockerfile**! `WORKDIR` автоматично створить папку, якщо її немає, і встановить контекст для всіх наступних інструкцій.

```dockerfile
# ❌ Погано: 'cd' діє ТІЛЬКИ в межах одного RUN і скидається на наступному рядку!
RUN mkdir /app
RUN cd /app
COPY app.py . # Файл потрапить у корінь або дефолтну папку, а не в /app!

# ✅ Добре: Створює папку і надійно фіксує контекст
WORKDIR /app
COPY app.py .
```

## ⭐ Додаткові важливі правила безпеки

### 🔒 11. Не запускайте від `root` (Non-Root USER)
За замовчуванням контейнери виконуються з правами `root`. Якщо зловмисник скомпрометує застосунок, він може отримати доступ до хост-системи.
```dockerfile
RUN groupadd -r appuser && useradd -r -g appuser appuser
USER appuser
```

### 🙈 12. Завжди створюйте `.dockerignore`
Запобігає копіюванню секретів, локальних віртуальних середовищ (`.venv`, `node_modules`), історії `.git` та тимчасових файлів у контейнер.

### 🔑 13. Ніколи не зашивайте паролі та секрети у Dockerfile
Використовуйте змінні середовища під час запуску (`docker run -e ...` / `--env-file`) або Docker Secrets.

### ⚡ 14. Використовуйте Exec Form для CMD та ENTRYPOINT
```dockerfile
# ❌ Shell Form: запускається через /bin/sh -c (сигнали SIGTERM блокуються)
CMD python app.py

# ✅ Exec Form: запускається напряму (контейнер миттєво і коректно зупиняється)
CMD ["python", "app.py"]
```
